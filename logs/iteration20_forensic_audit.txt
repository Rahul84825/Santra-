1. EXECUTIVE SUMMARY & EVIDENCE RECONCILIATION
--------------------------------------------------------------------------------
This forensic audit was performed prior to any code modifications. Two critical
defects reported in the runtime logs and screenshot were investigated:
1. Conversation Streaming Failure: "NameError: name 'sanitize_speech_text' is not defined"
2. Windows Process Crash: Exit code 3221226505 (Hex: 0xC0000409, STATUS_STACK_BUFFER_OVERRUN)
3. Command Palette Disappearance & App Exit: Premature dialog closure, lack of lifecycle
   tracking, unsafe cross-thread QTimer invocations, and DWM window flag recreation.

2. EVIDENCE A: CONVERSATION STREAMING FAILURE ("sanitize_speech_text")
--------------------------------------------------------------------------------
Location: core/jarvis_runtime.py (line 1434)
Observed in log:
  logs/jarvis.log:26910: [DEBUG] - Jarvis.ConversationManager - [CmdWorker-7A2E90] -
  [CONVERSATION] Streaming exception: name 'sanitize_speech_text' is not defined

Root Cause:
- In core/jarvis_runtime.py, the streaming sentence callback `_on_sentence_chunk(sentence)`
  invokes `clean_chunk = sanitize_speech_text(sentence)`.
- However, `sanitize_speech_text` was never imported into core/jarvis_runtime.py from
  `core.speech_sanitizer`.
- When streaming tokens from the NVIDIA provider, the callback failed with a NameError.
- ConversationManager intercepted the streaming exception and fell back to non-streaming
  `reason_and_execute`, resulting in duplicate latency, dropped streaming tokens, and
  fallback responses (such as "Sir, I am ready to explain, but you have not specified
  the subject matter." or unparsed "Thought: ..." tokens).

Fix:
- Import `sanitize_speech_text` into core/jarvis_runtime.py.
- Ensure streaming callbacks in ConversationManager and JarvisRuntime have complete
  exception isolation and fallback preservation.
- Sanitize "Thought:" and internal scratchpads before any TTS or UI display.

3. EVIDENCE B: PROCESS TERMINATION EXIT CODE 3221226505 (0xC0000409)
--------------------------------------------------------------------------------
Exit code 3221226505 = 0xC0000409 (STATUS_STACK_BUFFER_OVERRUN / __fastfail).
Windows Application Event Log confirmed:
  Faulting application name: pythonw.exe
  Faulting module name: Qt6Core.dll, version: 6.11.1.0
  Exception code: 0xc0000409
  Fault offset: 0x000000000001cf68

Root Cause Analysis:
In PyQt6/Qt6Core, __fastfail(FAST_FAIL_FATAL_APP_EXIT) is triggered by `qFatal` whenever:
a) A QObject method is invoked or created from a foreign non-Qt thread.
   Specifically discovered in ui/panels/spotify_panel.py:
   Line 590: `threading.Thread(target=self._background_poll, daemon=True).start()`
   Lines 597-598: `QTimer.singleShot(0, lambda: self._update_playback_ui(state))`
   `QTimer.singleShot` was being executed directly inside a Python background thread!
   In Qt6, `QTimer` cannot be instantiated or operated on a non-Qt thread without a
   QThread event loop. When the timer dispatches or when the dialog closes, Qt aborts.
b) DWM Window Flag Mutation in ui/panel_controller.py:
   Lines 95-98:
     `self.window.setWindowFlags(self.window.windowFlags() | Qt.WindowType.WindowStaysOnTopHint)`
     `self.window.show()`
     `self.window.setWindowFlags(self.window.windowFlags() & ~Qt.WindowType.WindowStaysOnTopHint)`
     `self.window.show()`
   Calling `setWindowFlags` on an active, shown top-level window destroys and recreates the
   underlying native Win32 HWND. When modal child dialogs or active mouse/keyboard events
   are in-flight, this invalidates native window hierarchy and triggers Qt assertions.

Fix:
- Eliminate `QTimer.singleShot` calls from background threads. Use thread-safe Qt Signals.
- Replace unsafe `setWindowFlags` toggles with Win32 `SetWindowPos` or safe Qt `raise_()` /
  `activateWindow()`.
- Add global Qt message handler and `sys.excepthook` to log any fatal Qt warnings before abort.
